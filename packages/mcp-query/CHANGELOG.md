# @johnhenry/mcp-query

## 0.7.0

### Minor Changes

- 3363512: OAuth debugging and inbound auth. `instrumentAuthProvider` now records which registration mechanism produced the client (`cimd` or `dcr`), what discovery offered (CIMD support, DCR availability, `iss` support, DPoP algorithms), an `issuerCheck` step once the code-exchange leg starts, and the DPoP key thumbprint only (never the key); `authNote()` lets a host add its own steps. `@johnhenry/mcp-query/server` gains `inboundAuth` on `createGateway` / `createGatewayHandler` plus `applyInboundAuth`: a host-verified bearer token (`requireBearerAuth` / `verifyBearerToken`) is mapped into the call `_meta` (`principal`, `partition`, `authScopes`, `authClientId`) at one choke point covering every registered handler (tasks, skills and extension pass-through included), and caller-supplied values for those keys are dropped.
- e3f8f5c: Opt-in connection preflight from a Server Card: `ConnectionConfig.cardPreflight: { cardUrl, serverUrl?, fetch?, allowInsecureLocalhost?, timeoutMs? }` fetches the server's card (hardened discovery fetch, 3s default budget) before a fresh connect and uses the protocol versions it lists as the connection's `versions`, so a modern-only or legacy-only server is reached without a failed probe. It is advisory only: a card that cannot be fetched or parsed is ignored, a connect that fails with the card's versions retries once with the connection's normal configuration, explicit `versions` / `versionNegotiation` win (the card is not fetched), and everything after connecting comes from the live server. Also exports `cardProtocolVersions(options)` from `@johnhenry/mcp-query/discovery`.
- 3cc0f6e: Deprecation notes for the features MCP 2026-07-28 deprecates. `@deprecated` JSDoc now points at SEP-2577 and the twelve-month minimum window (SEP-2596) on the sampling and roots handler options and on the logging options (`defaultLogLevel`, `CallContext.logLevel`, `setLogLevel`), and on the `SSEClientTransport` re-export from `@johnhenry/mcp-query/transports` (HTTP+SSE is reclassified Deprecated by SEP-2596). In development, a modern-era server that asks for sampling or roots now triggers a one-time `console.warn`; silence it with `silenceDeprecationWarnings()` or `MCP_QUERY_SILENCE_DEPRECATIONS=1`. It never fires in production or under test runners. The optional `_meta` the draft revision restores on sampling, elicitation and roots types now passes through the handlers and the `InteractionBroker` in both directions: a `roots` handler receives the request's `_meta` and may return `{ roots, _meta }` (a plain array still works), and an elicitation `InteractionDecision` can carry `_meta` onto the result.
- 7f4791b: Client support for the MCP Events extension (`io.modelcontextprotocol/events`, SEP-3415, Beta, protocol 2026-07-28+): `connection.supports("events")`, `client.listEvents(server?)` (cached under the SEP-2549 helpers, invalidated by `notifications/events/list_changed`), and `client.events(server, name, input, opts)` returning a subscribable (`subscribe` / `getSnapshot` / `close` / `refresh`) that polls `events/poll`, honours `nextPollMs` and `hasMore`, resumes from its last cursor across failures and reconnects, dedupes on `eventId`, and reports `truncated: true` as an explicit gap. Poll delivery only: `mode: "stream"` rejects with a clear `MCPError`, and webhook subscription is not driven. Built on mcp-query-defined schemas over the SDK's raw `request()` with a runtime probe for whether the installed SDK era-gates `events/*`, so it works on SDK 2.0.0. Every list and poll runs through the interceptor chain as a new `event` operation kind (`OperationKind` and `CallAuditEntry.kind` gain `"event"`; an interceptor that passes unknown kinds to `next` is unaffected, and a policy that denies unknown kinds will now deny events). New: `useEventTypes` / `useEvents` in `/react`; `verifyEventWebhook` / `generateWebhookSecret` in `/server` (Standard Webhooks receiver-side check); `MockMCPServer({ events })` with a controllable source in `/testing`.
- 1a9f81b: EXPERIMENTAL, may change: opt-in prototype of the MCP file uploads/downloads extension (`io.modelcontextprotocol/files`, a working-group draft with no SEP and no SDK support). Enable with `new MCPClient({ experimental: { files: true } })`; nothing changes for anyone who does not. `callTool` accepts `Blob` / `File` / `{ name, mimeType, data }` for `x-mcp-file` params (inline within the server's `maxInlineBytes`, `accept` / `maxSize` checked first), handles `resultType: "upload_required"` as a retry round next to `input_required` (each upload is its own audited `extension` operation, `files/upload`, through the interceptor chain; HTTPS only, no redirects, private addresses refused, `credentials: "include"` only for allowlisted hosts, `expiresAt` and the call's `signal` respected, injectable `fetch`), and `client.fetchDownload()` fetches a result's download target (size and digest checked, never written to disk). Interim results and calls that carried files are never cached; results carrying download URLs get a staleTime capped at their expiry. `MockMCPServer({ files })` and `MockUploadSink` are test fixtures. Limit, probed on `@modelcontextprotocol/client` 2.0.0: on the 2026-07-28 wire the SDK rejects `upload_required` before mcp-query sees it, so the out-of-band upload flow cannot complete there (reported as a clear `MCPError`; `upload` is therefore not declared by default). Inline transfer and downloads work. See `docs/files-extension.md`.
- a1dfc17: Gateway: extension negotiation and pass-through (#82 items 3, 4, 5). `createGateway` / `createGatewayHandler` take an `extensions` option and compute `capabilities.extensions` from what upstreams advertise and policy allows, offering an extension only to a consumer that declared it, and telling the upstream exactly what the consumer declared (per-request client capabilities on modern connections). MCP Apps (`io.modelcontextprotocol/ui`) now negotiates through the gate: `_meta.ui` and `ui://` resources pass through to declaring consumers only. Tasks (`io.modelcontextprotocol/tasks`): task handles are forwarded to declaring consumers with namespaced, HMAC-signed `taskId`s bound to the partition and principal (no server-side state; `extensions.tasksSecret` shares them across instances), `tasks/get|update|cancel` route to the owning upstream through the interceptor chain, and a consumer that did not declare tasks still gets the final result. Skills (`io.modelcontextprotocol/skills`): `skills/list` / `skills/get` aggregate upstreams with the origin in each `skill://` URI, and file reads route back byte-for-byte (never rewritten). New opt-in `extensions.passthrough` re-serves allowlisted unknown extension methods. New `MCPClient.forward()` sends a raw request through the interceptor chain; `Operation.kind` / `CallAuditEntry.kind` gain `"task"` and `"extension"`; `AuthzRequest.method`; new gateway options `partitionFrom`, `skillFilter`, `audit`; `AnswerGuardRequest.kind` gains `"task"`.
- fc9a255: Gateway stateless-era details and routing headers (#82 items 6 and 7). `createGatewayHandler` rejects a request whose `Mcp-Method` / `Mcp-Name` / `Mcp-Param-*` headers disagree with the body with HTTP 400 and `HeaderMismatch` (-32020), including the `Mcp-Param-*` check the SDK's low-level server does not do and the `tasks/*` and `events/*` names. `CallContext.routing` / `CallAuditEntry.routing` carry the body-verified method, name and `x-mcp-header` values for policy, rate limits and audit. The consumer's `clientInfo`, `logLevel` and `traceparent` / `tracestate` / `baggage` now traverse the gate; aggregated lists carry the minimum upstream `ttlMs` and `cacheScope: "public"` only when every upstream said so and the list was not filtered (including `resources/templates/list`, which had no hint); lists are returned in a deterministic order. The client sends `Mcp-Param-*` headers on the task-augmented `tools/call`, on `events/*` (re-listing and retrying once on HeaderMismatch) and on `forward()` with an `inputSchema`, and records each upstream list's `cacheScope` in its cache entry.
- d1839fe: Skills over MCP, the rest of the client side. `client.readSkillDirectory(uri, server)` (also on `scope()`) reads a skill directory over `resources/directory/read` when the server advertises `directoryRead` (a clear `MCPError` otherwise), cached under the server's ttl and run through the interceptor chain as a `skill` operation. `CallContext.meta` now travels as `_meta` on `skills/list`, `skills/get`, directory reads and the `resources/read` behind `readSkillFile`: the SDK's `SkillsClient` takes no `_meta`, so it is given a view of the SDK `Client` that injects it. New opt-in `MCPClientConfig.skillApproval` (default off, needs `interactions`) routes the first read of a skill through the `InteractionBroker` (`gate("confirm", ...)`, payload `{ action: "skill-load", ... }`), bound to the manifest's digest set so a changed manifest asks again; a denial is an `MCPError` and nothing is cached. Verified skill files also use the configured `cacheStore` (digest-keyed, re-hashed against the manifest on read-back, `cacheScope` respected). Adds `skillFileCacheKey`, the `SkillDirectory` / `SkillApprovalConfig` types, and `MockMCPServer` `skillsDirectoryRead` + `skillMetaLog`.

## 0.6.0

### Minor Changes

- a3ab7bb: Add a `@johnhenry/mcp-query/browser-bundle` export: one self-contained, minified ESM file (`dist/browser/mcp-query.browser.js`) with the MCP SDK client, zod and agent-query-core inlined, plus the browser-safe parts of `@johnhenry/mcp-gate` (`createGateClient`, policy and redaction helpers). One import in a browser makes no further requests, so hosts can pin and vendor it. React hooks stay out of the bundle. Existing export paths are unchanged. The README has a size table (`npm run size-table`).
- 8596e26: Forwarded interaction rounds (`interactions: "forward"`) now guard the consumer's answers on their way upstream. mcp-gate applies its `redact` rules to `inputResponses` (never to `requestState`, which stays byte-for-byte), and a new `answerPolicy` config (rules or a function receiving an `AuthzRequest` with `kind: "answer"`) gives allow / deny / approve a say per answer: a denied answer becomes `{ action: "decline" }`. With no `answerPolicy`, answers are allowed as before. The answer hop's audit entry records `redactedFields` and `declined` (names only). mcp-query adds the `guardAnswers` gateway option and its types, `AuthzRequest.kind: "answer"`, and the audit fields. It also fixes the gateway's `-32004` `GatewayUpstreamCapabilityError` translation, which never fired because `MCPClient` wraps the SDK error in an `MCPError` first: consumers of an `answer`/`deny` gateway now get `-32004` instead of the upstream's raw `-32021` (forwarding gateways keep `-32021`, which names the consumer's own missing capability).
- 103acf6: Gateway MRTR pass-through (#82, slice 1). `createGateway` / `createGatewayHandler` take `interactions: "answer" | "forward" | "deny"` (or `{ default, upstreams }`): with `"forward"`, an upstream `input_required` result on a 2026-07-28 connection is returned to the gateway's consumer (`requestState` untouched) and the consumer's retry is routed back to the same upstream; the default `"answer"` is unchanged. `MCPClient.callTool` / `getPrompt` accept `interaction` (manual MRTR), an interim `input_required` result is never cached, and `CallAuditEntry` gains `interaction`. `@johnhenry/mcp-gate` adds the `interactions` config key, a fail-closed `urlElicitation` allow/deny host policy for forwarded URL-mode elicitations, and redaction that leaves `requestState` alone.
- f93f134: The interceptor chain now covers `getPrompt` (`kind: "prompt"`), the skills calls `listSkills`/`getSkill`/`readSkillFile` (`kind: "skill"`) and the catalogs behind `listTools`/`listResources`/`listResourceTemplates`/`listPrompts` (`kind: "list"`, run where the catalog is fetched or re-fetched, so the synchronous accessors return what the chain answered and a throwing interceptor hides the catalog). New: `OperationKind` gains `list | prompt | skill`, `Operation.method`, `CatalogName`, async `client.discover(catalog, server?, { context })` (also on `scope()`, plus `scope().getPrompt`), and `listFilter({ keep, annotate })` in `@johnhenry/mcp-query/server`. Interceptors written against `read | call | query` keep working if they pass other kinds to `next`. `authorize()` treats `"approve"` on a `list` as allow, `rateLimit` and `circuitBreaker` skip `list`, and a synchronous throw from an interceptor is now audited like an async one. An `authorize` policy that denies every kind it does not recognise will now also deny the new kinds.
- 739cf37: Add `@johnhenry/mcp-query/discovery`: Zod schemas for MCP Server Cards (SEP-2127) and the AI Catalog envelope, `fetchServerCard(url, opts)`, `discoverFromDomain(domain, opts)` (reads `/.well-known/ai-catalog.json`), remote URL resolution, and `compareCardToLive` to flag disagreement with a live server. Fetches are HTTPS-only (loopback http behind an explicit option), size-capped, time-limited, refuse cross-origin redirects, check the content type and accept an injectable `fetch`; results are untrusted display data and nothing is registered or connected.
- 5766b56: Skills over MCP (`io.modelcontextprotocol/skills`, SEP-2640): `connection.supports("skills")`, `client.listSkills(server?)`, `client.getSkill(uri, server)` and `client.readSkillFile(skill, ref?)` built on the SDK's `SkillsClient`, so size, digest and frontmatter verification is the SDK's and failures surface as `MCPError` with the reason preserved (`skillVerificationReason`). Listings honor SEP-2549 `ttlMs`/`cacheScope`, are keyed per server and `client.scope()` partition, go stale on `resources/list_changed`, and verified files are cached by manifest digest. Adds `useSkills` / `useSkill` and a `MockMCPServer` `skills` fixture (including tampered-digest/size/frontmatter cases). Needs `@modelcontextprotocol/client` >= 2.4.0 at call time; the peer range is unchanged and older SDKs get a clear `MCPError` naming the minimum version.
- 98c45c2: Tasks extension (`io.modelcontextprotocol/tasks`, SEP-2663) now works on 2026-07-28 connections when the installed `@modelcontextprotocol/client` is 2.3.0 or newer: `callToolTask`, `getTask`, `cancelTask` and `input_required` rounds via `tasks/update`. The unconditional modern-era gate is replaced by a runtime probe of the SDK, so SDK 2.0.x (still within the `^2.0.0` peer range) fails fast with an accurate message that names the 2.3.0 requirement. Modern-era task status is poll-only because the SDK client has no `taskIds` filter for `subscriptions/listen`.

## 0.5.0

### Minor Changes

- 999aba4: `queryTool(name, args, { signal })` lets a caller cancel its own wait: that caller's promise rejects with an `AbortError` when its signal fires (immediately, without starting a request, if it is already aborted). The underlying request, which is de-duplicated across callers, is cancelled only once every caller waiting on it has aborted; a cancelled fetch no longer marks the cache entry as errored. `MockMCPServer` tool handlers also receive the request's `signal` on their context.

## 0.2.2

### Patch Changes

- 48b6dad: Widen the `@modelcontextprotocol/client` and `@modelcontextprotocol/server` ranges from the exact `2.0.0` to `^2.0.0`, so consumers on any 2.x SDK install without `ERESOLVE` peer warnings. In `@johnhenry/mcp-query` these are peer dependencies; in `@johnhenry/mcp-gate` they are regular dependencies, so the wider range lets npm dedupe to the single SDK copy the consumer already has instead of installing a second 2.0.0. The suite passes against SDK 2.0.0 (the floor) and the latest 2.x (2.3.1), and CI now runs the SDK-using packages against both (#42).
