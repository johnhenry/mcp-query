EXPERIMENTAL, may change: opt-in prototype of the MCP file uploads/downloads extension (`io.modelcontextprotocol/files`, a working-group draft with no SEP and no SDK support). Enable with `new MCPClient({ experimental: { files: true } })`; nothing changes for anyone who does not. `callTool` accepts `Blob` / `File` / `{ name, mimeType, data }` for `x-mcp-file` params (inline within the server's `maxInlineBytes`, `accept` / `maxSize` checked first), handles `resultType: "upload_required"` as a retry round next to `input_required` (each upload is its own audited `extension` operation, `files/upload`, through the interceptor chain; HTTPS only, no redirects, private addresses refused, `credentials: "include"` only for allowlisted hosts, `expiresAt` and the call's `signal` respected, injectable `fetch`), and `client.fetchDownload()` fetches a result's download target (size and digest checked, never written to disk). Interim results and calls that carried files are never cached; results carrying download URLs get a staleTime capped at their expiry. `MockMCPServer({ files })` and `MockUploadSink` are test fixtures. Limit, probed on `@modelcontextprotocol/client` 2.0.0: on the 2026-07-28 wire the SDK rejects `upload_required` before mcp-query sees it, so the out-of-band upload flow cannot complete there (reported as a clear `MCPError`; `upload` is therefore not declared by default). Inline transfer and downloads work. See `docs/files-extension.md`.
