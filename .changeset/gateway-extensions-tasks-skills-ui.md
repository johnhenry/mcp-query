Gateway: extension negotiation and pass-through (#82 items 3, 4, 5). `createGateway` / `createGatewayHandler` take an `extensions` option and compute `capabilities.extensions` from what upstreams advertise and policy allows, offering an extension only to a consumer that declared it, and telling the upstream exactly what the consumer declared (per-request client capabilities on modern connections). MCP Apps (`io.modelcontextprotocol/ui`) now negotiates through the gate: `_meta.ui` and `ui://` resources pass through to declaring consumers only. Tasks (`io.modelcontextprotocol/tasks`): task handles are forwarded to declaring consumers with namespaced, HMAC-signed `taskId`s bound to the partition and principal (no server-side state; `extensions.tasksSecret` shares them across instances), `tasks/get|update|cancel` route to the owning upstream through the interceptor chain, and a consumer that did not declare tasks still gets the final result. Skills (`io.modelcontextprotocol/skills`): `skills/list` / `skills/get` aggregate upstreams with the origin in each `skill://` URI, and file reads route back byte-for-byte (never rewritten). New opt-in `extensions.passthrough` re-serves allowlisted unknown extension methods. New `MCPClient.forward()` sends a raw request through the interceptor chain; `Operation.kind` / `CallAuditEntry.kind` gain `"task"` and `"extension"`; `AuthzRequest.method`; new gateway options `partitionFrom`, `skillFilter`, `audit`; `AnswerGuardRequest.kind` gains `"task"`.
